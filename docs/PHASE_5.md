# Phase 5 — release candidate and acceptance

Version **1.0.0rc1**, prepared 2026-11-13. The application work below is implemented. Production certification is **pending** the external evidence listed below; neither a working preview/production URL nor a full real-data audit is claimed.

## Implemented

- [Production settings](../src/competitive_intelligence/config.py) reject process-local storage, absent/short/placeholder launch codes and missing trusted hosts. Request bodies are capped at 16 KiB. Supplier/profile IDs must be unique. HTTPS source links reject credentials, malformed authorities, control characters and nonstandard ports.
- [Audit admission](../src/competitive_intelligence/services/sql_repository.py) serializes quota checks and enqueue in the same transaction using `sys.sp_getapplock` with transaction ownership, a fixed resource and a five-second timeout. Existing `ci.audit_runs` provides rolling minute/day counts and pending-work counts; no schema changes, seeders or new tables are required. All HTTP launches use this path. Lock or database failures never fall back to memory. Verify the application principal can acquire this lock in the isolated Azure acceptance environment.
- Shared defaults are **5 launches/rolling minute**, **30/rolling 24 hours**, **10 pending audits**. They include fixture and live launches across clients/instances. Worker attempt and per-attempt model caps remain independent. Daily limits are admission bounds, not currency/billing guarantees. `429` includes conservative `Retry-After` seconds. Tune `AUDIT_LAUNCHES_PER_MINUTE`, `AUDIT_LAUNCHES_PER_DAY`, `AUDIT_MAX_PENDING` together with provider account spending limits.
- The bounded process-local IP limiter slows unauthorized attempts; its client map is capped at 10,000 entries and expired windows are reclaimed. **Deploy an edge/WAF rate rule on POST `/api/v1/audits`** to control unauthorized attempts across serverless instances. Forwarded client-IP headers are not trusted by application code. Shared authenticated admission works independently of IP identity.
- [Application responses](../src/competitive_intelligence/app.py) use fresh server-generated request IDs, generic unexpected/database errors, no-store for API/HTML/health, restrictive CSP, frame/permissions headers and HSTS on secure production requests. Unexpected-error logs contain only request ID and exception class. Keys, prompts, SQL and connection strings are not logged by these handlers.
- `/health/live` checks process availability. `/health/ready` performs a short database connectivity read and reports `durable` vs `demonstration`; it does not certify the entire schema or a worker. The worker's `check-db` remains the read-only schema/driver check. Startup opens no database connection.
- [Result validation](../src/competitive_intelligence/schemas/audit.py) rejects duplicate IDs, missing evidence/verdict rows, cross-source claim provenance, dangling evidence IDs, incompatible briefing citations and incorrect matrix counts. Stored incompatible results fail safely; approved public DTOs continue to exclude private traces.
- Final rule-scope review reproduced and fixed two errors: unsupported price ranks no longer run the “cheapest” calculation, and percentage claims cannot compute an unselected consumption profile. Both abstain with a human-review flag.
- [Reviewed product bindings](../src/competitive_intelligence/services/reference_bundle.py) can attach a product to an extracted claim only on exact supplier, HTTPS URL, canonical hash, normalized literal quotation and validity interval. Review must precede claim capture. Ambiguous bindings and unknown reference products are rejected. Claims retain a binding digest and review timestamp, separate from `human_reviewed`. A page change invalidates the binding. Existing approved baseline products are preserved. Without a matching binding, price claims abstain.
- [Worker](../src/competitive_intelligence/worker.py) responds to SIGTERM/SIGINT by finishing the current delivery with heartbeats, then exiting before claiming more work. Poll waits are interruptible. Forced termination still relies on fenced lease recovery. `run --once` exits unsuccessfully for a terminally failed delivery.
- [Evaluation](../src/competitive_intelligence/evaluation.py) and [annotation instructions](../eval/README.md) provide one-to-one source/hash/quote matching, exact denominators, parameter accuracy, all-gold and conditional metrics, confusion counts and an explicit reviewed-data gate. The [24 source-backed candidates](../eval/review-candidates.json) have **null annotations**. The separate 24-case synthetic price/green regression is not a human golden set or a model-quality estimate.
- [Preview smoke command](../src/competitive_intelligence/release.py) checks homepage/security headers, live/ready health, durable storage, approved latest, saved completed state, three-supplier price/green scope, unknown audit handling and fail-closed launch auth. It sends no valid access code, enqueues no audit, follows no redirects and bounds time/response bytes. `--allow-fixture` is demonstration-only and still cannot make memory storage pass durable readiness.
- [CI](../.github/workflows/ci.yml) installs from the lockfile, runs offline pytest and the fixture demonstration, then builds the package without service secrets. Pytest belongs to the development dependency group. Browser requests have a 15-second timeout, credentials clear even on network failure, and polling displays recovery status.

## Release procedure

1. Run `uv sync --locked`, `uv run pytest -q`, `uv run fact-or-watt-fixture-audit`, `uv build`. CI must pass on the target Linux runtime; local Windows success does not prove Linux driver/network behavior.
2. Complete independent analyst annotations for 20–30 claims across three suppliers and price/green. Curate a reviewed reference bundle using original document hashes, product IDs, dates, common D02d region and VAT scope. Run the model against the exact saved evaluation texts, then run `fact-or-watt-evaluate ... --require-reviewed`. Save the report and the model/run identifier. Default score floor is 0.9 and is configurable; document any accepted threshold explicitly.
3. Provision preview web/worker secrets separately from production. Set `APP_ENV=production`, `DATABASE_URL`, `AUDIT_ACCESS_CODE` (unique, random, at least 16 characters), `TRUSTED_HOSTS` (exact preview domain), provider/model settings and a deployment-accessible `REFERENCE_BUNDLE_PATH`. Install the worker with `uv sync --locked --no-dev`. Do not use the local example access code. No repository schema/bootstrap action is required.
4. Verify approved Vercel-to-Azure egress, TLS certificate validation, driver import, connection limits and the manually provisioned schema using `uv run fact-or-watt-worker check-db` in the actual worker runtime. Configure the same narrow Azure network policy for the preview runtime. Do not broaden the firewall to bypass a failed check.
5. On a separate isolated Azure database, run the opt-in integration suite with `RUN_AZURE_INTEGRATION=1` and `TEST_DATABASE_URL` distinct from production. The existing tests wrap writes in rollback transactions; they do not prove a real cross-connection commit/restart or lock contention. Separately record a committed acceptance audit in the isolated environment: recreate web/worker processes, confirm persistence, race independent admission/worker connections, interrupt an owned delivery, wait for lease expiry, and verify retry fencing/idempotent completion. Never use production as a substitute test target. If no isolated database is available, retain this release gate as pending.
6. Start the separately hosted worker using `uv run fact-or-watt-worker run`. Set host termination grace to exceed a normal audit's bounded run time when possible; shorter grace periods recover by lease expiration. Monitor worker restarts, pending queue age, failed jobs, provider caps and database health. Web health alone does not establish worker liveness.
7. Launch one authorized **live** three-supplier audit in the acceptance environment. Inspect literal quotations, product bindings, source origins/timestamps, reference validity, deterministic outcomes, warnings and private hashed agent events. A snapshot is visibly dated; an unavailable model or reference never becomes affirmative evidence. Approve only after review with `uv run fact-or-watt-worker publish AUDIT_ID --approved-by REAL_OPERATOR`. Keep the completion trace with the release record.
8. Deploy Vercel preview and run `uv run fact-or-watt-check-preview https://ACTUAL-PREVIEW.vercel.app`. Exercise wrong/missing auth, configured edge limits, oversized input, transient database loss, model timeout, source fallback, result reload and worker restart. An approved fixture is suitable for a demo; production acceptance requires the live scope. Record checks and URLs before promoting the preview to production, then repeat smoke checks there.

## Failure and rollback operations

### Launch button and worker feedback follow-up

A browser reproduction with a delayed latest-audit response exposed a launch race: the homepage awaited that independent database read before registering the submit handler. Submitting during the wait used the native GET form behavior and reloaded the homepage without creating a job. The handler is now registered before the read starts, and the submit button remains disabled until initialization is complete. The same delayed-response reproduction now opens a completed nine-claim offline audit while the latest panel is still loading.

The worker now logs startup/schema checking, readiness and each claimed audit immediately. These messages contain no connection strings or credentials. Restart the Flask and worker processes and hard-refresh the browser to load this fix. In the worker terminal, expect `Worker starting`, then `Worker ready`, and `Audit ... claimed; processing started` when an eligible job is picked up. The previous completion JSON remains available. Focused persistence/API/journey checks passed (53 tests), the full suite passed with **294 passed, 5 skipped**, and the package was rebuilt. Editor diagnostics reported no errors. This verifies the application fixes; it does not assert that an external worker has claimed the existing Azure jobs.

- **Database unavailable:** readiness and affected reads/launches return 503; liveness still identifies the web process. Restore the approved network path/database. No audit is substituted from memory. An interrupted worker's lease eventually expires and another worker resumes within the stored attempt bound.
- **Model timeout or exhausted budget:** the evidence pipeline warns and abstains; it does not infer proof or publish automatically. Inspect private hashed traces and provider account usage. Use explicit operator review before rerunning an expensive audit.
- **Stop new launches:** remove `AUDIT_ACCESS_CODE` from development/demo, or disable the POST route at the production edge while preserving public reads. Production intentionally refuses startup without its code, so do not remove it from a serving production process as an availability control. Stop workers after current work to freeze new processing. Rotate the code for compromised credentials; existing queued jobs remain durable.
- **Rollback code:** restore the previous verified Vercel deployment and the matching worker release/lockfile, keeping the existing Azure schema and data. Stop the newer worker first. No automatic migrations or downgrades run. Verify DTO compatibility with the approved publication before rollout; incompatible stored results return `STORED_AUDIT_INCOMPATIBLE` instead of partial output.
- **Rollback publication:** after inspecting the old completed result, republish its audit ID using the explicit operator command. This changes the current publication transactionally and retains the underlying audit. A failed/incomplete audit cannot be published.
- **Source/reference change:** retain original artifact hashes and source dates. Changed source text invalidates reviewed product bindings. Curate and review a new bundle/baseline instead of editing historical evidence in place.

## Acceptance record

### Live runtime corrections (2026-11-14)

An operational run of the user's queued audits exposed issues not covered by the original in-memory source adapter:

- SQL Server rejects `BIT IS 1`. Baseline approval and human-review filters now use equality to `true()`, which compiles to `= 1`. The failing query was reproduced using SELECT only in Azure; both corrected filters and all eight registered baseline readers were then read successfully. Dialect compilation regressions cover both actual adapter statements.
- Existing `ci.source_captures.captured_at` and `ci.audit_sources.checked_at` are `datetime2(3)`. Durable scouting now creates capture/check timestamps at millisecond precision before constructing either source DTOs or archive rows. The archive rejects over-precise direct writes instead of silently losing capture identity. A regression simulates database timestamp precision and verifies live-to-archive identity and restart timestamps.
- The engine permits three simultaneous connections. Durable intake now uses two source tasks, reserving one connection for the lease heartbeat. Four simultaneous source tasks previously caused SQLAlchemy connection-pool timeouts while waiting for fenced writes.

The queued fixture completed against Azure. Earlier failed live records are retained, and a new live request was submitted through the authenticated local app after these corrections. Runtime completion is recorded separately; passing offline tests alone is not treated as proof that this live request completed. The combined VS Code task is in [tasks.json](../.vscode/tasks.json); it starts the web process and worker in separate terminals.
